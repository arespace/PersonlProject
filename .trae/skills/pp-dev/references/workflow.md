# 协作流程与批次节奏

本文件约定人机分工、会话纪律、完成定义与批次节奏。与其它 reference 冲突时，以本文件为准，并回头修正对应文档。

## 1. 三层分工

| 层 | 谁 | 权限 | 产物 |
|---|---|---|---|
| 分析层 | 助手（可多会话并行） | 只读：不改代码、不碰编辑器、不提交 | 分析文档 |
| 决策层 | 用户 + 助手 | 只做选择，不写代码 | 批次清单、顺序、边界、验收标准 |
| 执行层 | 一个会话 | 独占改代码与提交 | 一个批次的可运行改动 |

规则：

- 分析层每份产出必须当场转成**不超过 5 条可执行项**；转不出来的只当资料，不进待办。
- 决策层在 10 分钟内完成：从待办里挑批次、定顺序、定边界、定验收标准。定不下来就缩小批次，不延长决策。
- 执行层一个会话只做一个批次，做完即提交。
- 同一时刻只允许一个执行会话改仓库。

## 2. 会话纪律

- 会话标题带前缀：`[分析]` / `[执行]` / `[决策]`。
- 一个功能 = 一个会话，不在同一会话里换主题；换主题就新开会话。
- 分析结论落到 `docs/superpowers/specs/` 或批次待办，不把聊天记录当唯一存档。
- 执行会话开工时先声明四件事：批次名、边界、验收标准、时间盒上限。

## 3. 编辑器与仓库的独占

- **编辑器是单实例**：同一时刻只允许一个执行会话要求用户操作编辑器（重编译、打开地图、移动资产、保存蓝图）。
- 编辑器被占用时，其它会话只准读：不准让用户切窗口、点保存、重启编辑器。
- Git 状态共享，执行类工作必须串行。开工前跑 `git status --short`，发现不属于本批次的未提交改动，先停下确认归属。
- 提交前再查一次 `git status`，只提交本批次文件，不用 `git add -A` 兜底。

## 4. 改前基线（必须记录）

动手前记录三项，写进批次说明：

1. **日志基线**：`Saved/Logs/PersonalProject.log` 当前的 Error / Warning 数量，至少摘录前 5 条。
2. **性能基线**：PIE 中 `stat fps` 或 `stat unit` 的当前帧数。
3. **流程基线**：当前能走通哪条链路（登录 → 大厅 → 战斗 → Boss / 篝火 → 死亡复活）。

改完用同样三项对比，判断是变好还是变坏。没有基线就不算验证完成。

## 5. 完成定义（缺一条不算完成，不许开下一个）

1. **编译通过**：关闭编辑器完整 Build.bat，输出 `Result: Succeeded`（不是 Live Coding 通过）。
2. **PIE 冒烟**：Listen Server + 1 客户端双端；进战斗；验证存档链路（本批次涉及存档/设置时做存盘 → 退出 → 重进，未涉及则至少重开一局且不依赖上一次会话的残留内存状态）；重开一局。
3. **蓝图配置清单勾完**：按 `blueprint-config.md` 输出并逐项确认；确实不需要配的项要写明原因，不能空着。
4. **一次提交**：一个批次一个 commit，消息说明「为什么」。

补充：提交前按 `code-review.md` 审查；有 P0 必须修完再提交。

## 6. WIP 上限

同时最多：

- 1 个批次在改代码
- 1 个批次在等验收
- 1 个批次在设计

第 4 个起排队，不并行开工。分析类会话不计入 WIP，但每份结论必须归入上述三类之一，否则按资料归档。

## 7. 半成品隔离

- 做一半的功能用蓝图布尔开关、入口隐藏、输入不绑定等方式关掉，不要留在关卡里被当成 bug。
- 开关默认值必须是「关」，并在批次说明里写清打开方式。
- 不允许用「注释掉一半代码」当隔离手段。

## 8. 时间盒

- 每个批次开工前给上限，按任务量估，不按日历拖。
- 到点未完成：砍范围，剩余部分拆成新批次，不延长本批次。
- 砍范围时优先保「能编译、主链路能跑通」，边缘情况移到下一批。

## 9. 收敛节奏

每周一次 30 分钟：

1. 结掉挂着的会话：分析结论转待办或丢弃。
2. 未提交改动：提交或回滚，不留半成品在工作区。
3. 分析文档转成不超过 5 条可执行项，进批次待办。
4. 检查 WIP 是否超限、时间盒是否连续超时。

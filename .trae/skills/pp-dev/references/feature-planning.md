# 需求澄清与实施计划

## 1. 先分流

| 变更规模 | 判定 | 流程 |
|---|---|---|
| 小改 | 单文件、无新接口/新字段、行为明确 | 直接改 → 构建 → 验证 |
| 中等 | 跨 2-3 文件，新增字段/事件/组件 | 先列方案，用户确认后改；不写正式文档 |
| 大型 | 新系统、跨模块、重构批次、需求含糊 | 设计文档 → 用户批准 → 计划文档 → 分任务执行 |

Bug 修复不走本节，走 `debugging.md`（根因优先）。

## 2. 澄清（只问会改变实现的问题）

1. **先读再问**：读用户点名的文件、相关模块、已有同名实现，能自己回答的不问。
2. 只问 1-2 个「答案会改变做法」的问题，例如：
   - 服务端权威还是客户端表现？
   - 走现有 GA 还是新 GA？走 EventBus 还是接口？
   - 是否需要蓝图可配？是否需要联机同步？
3. 用户没说的细节给出默认值，并明确说「这是默认，可改」，不要静默替用户决定。
4. 纯 UI/布局类需求，先给可看的 mockup（项目已有 `docs/LobbyUI_Mockup.html` 先例），比文字描述更快对齐。
5. 允许一次性 spike 验证技术可行性，但必须标注「throwaway」；spike 产物不能直接当正式实现继续堆，转正要重新走设计门。

## 3. 方案对比（大型变更）

动手前单独发一条消息，列 2-3 个真实可选方案：

- 每个方案说明：改哪些模块/文件、对现有系统的影响、联机与蓝图配置成本。
- 明确推荐一个并说明理由；只有一个合理方案时直接说清为什么其他方案不合适。
- 用户选定后再写设计文档。

## 4. 设计文档（大型变更必写）

路径：`docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`

最少包含：

- 目标与动因（为什么现在做）
- 范围：做什么 / 不做什么
- 方案与取舍（用户选定的那个）
- 影响的模块、类、数据表、蓝图资产
- 联机与权限模型（服务端权威点）
- 验收标准（可观测的行为）

**硬门**：设计文档未获用户批准，不写产品代码、不建资产、不装依赖。

## 5. 计划文档（大型变更必写）

路径：`docs/superpowers/plans/YYYY-MM-DD-<feature>.md`

每个任务必须包含：

- 文件清单：Create / Modify（带路径）
- 接口契约：本任务消费什么、产出什么（类名、函数签名、事件结构体）
- 步骤：改代码 → 编译 → 验证 → 提交（或批次内不提交）
- 验证方式：编译目标、PIE 场景、预期日志/行为

任务粒度：一个任务 = 一次可独立评审的交付；不要按「前端/后端」切，按「一个可验证的行为」切。

计划写完后自检一遍：

- 设计文档里的每条要求，是否都能指到某个任务？
- 后续任务用的类名/函数签名/字段名，是否与前面任务定义的一致？
- 是否还有「TBD」「处理边界情况」「补测试」这类不决定任何实现的空步骤？
- 计划长度是否超过它描述的代码量？超过就说明写成了代码誊抄。

UE 项目验证步骤写具体：

```text
1. 关闭编辑器，运行 Build.bat（见 build-and-verify.md），期望 Result: Succeeded
2. 打开 PIE（Listen Server + 1 客户端），进入 PPMap
3. 按 F 释放 Primary，期望：体力 -20、HUD 体力条下降、无 ClientActivateAbilityFailed 日志
4. 停止 PIE，检查 Saved/Logs/PersonalProject.log 无新增 Warning/Error
```

## 6. 重构批次规则

- 先阶段 A：单模块内解耦（接口化、去 Cast、去直调），编译 + PIE 通过。
- 再阶段 B：一次性拆/搬模块，不同时做业务改动。
- 禁止边优化边拆模块，禁止边优化边提交。
- 批次收尾固定四步：
  1. 完整编译（关编辑器）
  2. 双端 PIE 冒烟：进战斗、存档链路、重开一局（按 `workflow.md` 的完成定义执行）
  3. `code-review.md` 全量过一遍
  4. 统一提交（一个批次一个 commit）
- 批次中途发现范围膨胀：停下来告知用户，拆成下一批，不顺手扩。

## 7. 执行期

- 用 TodoWrite 建任务清单，完成一个标一个。
- 开工前先记录改前基线（日志 Warning 数、当前帧数、能走通的流程），对照项见 `workflow.md` §4。
- 每个任务结束后立即编译，不攒到最后一次编译。
- 改动涉及新 `UPROPERTY` / 新组件 / 新 `BindWidget` 时，同步准备 `blueprint-config.md` 的清单，不要等交付时回忆。
- 计划与实现冲突时，先更新计划再改代码，不静默偏离。

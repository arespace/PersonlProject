# P5.1 存档系统设计方案

> 状态：待评审 · 日期：2026-11-11 · 依据：`docs/计划/当前主线任务书.md` P5.1 节（六类范围不变）
> 本文只做设计，不含实现。审批通过后按第 8 节分批落地。

---

## 1. 目标与范围

### 1.1 目标

存档 → 退出 → 读档，六类数据逐项还原；篝火检查点作为重生点生效；无存档/损坏存档不崩溃。

### 1.2 做什么（六类，沿任务书不变）

| # | 类别 | 存什么 | 数据来源 | 怎么回到原处 |
|---|---|---|---|---|
| 1 | 角色进度 | `CharacterId` + 9 项属性 base 值（Health/MaxHealth/Mana/MaxMana/Stamina/MaxStamina/Attack/Defense/StaminaRegenRate） | `APP_PlayerState::GetSelectedCharacterId()`、`UPP_AttributeSet` | `PS->SetSelectedCharacterId()`（须在 `GrantAbilitiesForCharacter` 之前）；属性用 `SetNumericAttributeBase` 写回，服务端 ASC 自动复制 |
| 2 | 背包与金币 | `TArray<FPP_ItemInstance>` + `Gold` | `UPP_InventoryComponent::GetItems()/GetGold()` | 新增 `RestoreFromSave()`：服务端直接赋值数组 + 广播 `FPP_InventoryUpdatedEvent` |
| 3 | 已装备与槽位 | `TArray<FPP_EquippedItem>`（只存 ItemID + Slot，**不存 EffectHandle**） | `GetEquippedItems()` | `RestoreFromSave()` 内按 ItemID 重查 `DT_Items.EquipEffectClass`，重新 `ApplyEquipEffect` 并把新句柄写回数组；随后按槽位通知 `IPP_EquipmentUser` |
| 4 | 任务进度 | `TArray<FPP_ActiveQuest>`（含每个目标的 CurrentCount/bCompleted）+ `CompletedQuestIDs` | `QuestComponent::GetActiveQuests()/GetCompletedQuests()` | 新增 `RestoreFromSave()`：按 `QuestID` 回查 `DT_Task` 校正目标签名后赋值 + 广播 `FPP_QuestsUpdatedEvent` |
| 5 | 篝火检查点 | `bHasCheckpoint` + `CheckpointTransform` + `BonfireActorName` | `PlayerState::HasCheckpoint()/GetCheckpointTransform()`、当前休息的篝火名 | `PS->SetCheckpoint()`；读档后首次生成的落点直接取该 Transform（无检查点回退 PlayerStart） |
| 6 | 世界状态 | 采集点剩余次数、Boss 是否已击败、掉落的魂（金额 + 位置） | `APP_GatherableActor`（`RemainingGatherTimes`）、`APP_BossCharacter`、`APP_SoulPickupActor` | 服务端遍历关卡 Actor，按 **Actor 名**匹配后调各自的新增恢复接口；魂按存档数据重新 Spawn |

### 1.3 不做什么（明确排除，避免范围膨胀）

| 排除项 | 理由 |
|---|---|
| 玩家当前位置、朝向 | 魂类语义：读档一律回篝火/PlayerStart，避免读档后站在怪堆里 |
| Kills / Deaths / Score | 单局统计，跨局没有意义 |
| 普通敌人击杀状态 | 篝火休息本来就会重置半径内敌人，且敌人不参与进度 |
| 已锁定的目标、临时 Buff、投射物 | 瞬时运行时状态 |
| 多存档槽 / 云存档 / 存档加密 | v1 单槽；结构体保留 `SlotIndex` 字段，后续加槽不改序列化格式 |
| 游戏内读档（不重启世界直接回滚） | 需要销毁重建整个世界，风险远大于收益；读档入口只放在主菜单 |
| 联机客户端各自存档 | 存档只认房主/单人；客户端数据由服务端复制（见 §5） |

## 2. 序列化载体

### 2.1 载体选择：`USaveGame` 子类（不用 JSON / 自定义二进制）

- 项目已有先例 `UPP_LocalSaveGame`（昵称偏好），沿用 `UGameplayStatics::SaveGameToSlot/LoadGameFromSlot`。
- 选它的理由：UE 原生序列化能直接处理 `USTRUCT`/`FTransform`/`FName`，不需要自己维护读写顺序，字段增减对旧档天然宽容（缺字段保留默认值）。
- 不选 JSON：需要手写全部字段映射，且 `FName` 与枚举的容错要自己兜。

### 2.2 新增文件（Core 模块，零反向依赖）

`Source/PersonalProjectCore/Public/Save/PP_SaveTypes.h`（纯数据，无逻辑）：

```cpp
USTRUCT() struct FPP_SaveAttributeData   { float Health, MaxHealth, Mana, MaxMana, Stamina, MaxStamina, Attack, Defense, StaminaRegenRate; };
USTRUCT() struct FPP_SaveCharacterData   { FName CharacterId; FPP_SaveAttributeData BaseAttributes; };
USTRUCT() struct FPP_SaveInventoryData   { TArray<FPP_ItemInstance> Items; TArray<FPP_EquippedItem> Equipped; int32 Gold = 0; };
USTRUCT() struct FPP_SaveQuestData       { TArray<FPP_ActiveQuest> ActiveQuests; TArray<FName> CompletedQuestIDs; };
USTRUCT() struct FPP_SaveCheckpointData  { bool bHasCheckpoint = false; FTransform Transform = FTransform::Identity; FName BonfireActorName; };
USTRUCT() struct FPP_SaveGatherableState { FName ActorName; FName GatherableID; int32 RemainingGatherTimes = 0; };
USTRUCT() struct FPP_SaveBossState       { FName ActorName; FName EnemyID; bool bDefeated = false; };
USTRUCT() struct FPP_SaveSoulState       { int32 Amount = 0; FVector Location = FVector::ZeroVector; };
USTRUCT() struct FPP_SaveWorldData       { TArray<FPP_SaveGatherableState> Gatherables; TArray<FPP_SaveBossState> Bosses; TArray<FPP_SaveSoulState> Souls; };
```

`Source/PersonalProjectCore/Public/Save/PP_SaveGame.h`：

```cpp
UCLASS()
class PERSONALPROJECTCORE_API UPP_SaveGame : public USaveGame
{
    UPROPERTY() int32 SaveVersion = 1;      // 结构版本，不等于工程版本
    UPROPERTY() FDateTime SavedAt;
    UPROPERTY() FName MapName;              // 读档后要 ServerTravel 的目标地图
    UPROPERTY() FString PlayerName;
    UPROPERTY() int32 SlotIndex = 0;        // v1 固定 0，预留多槽
    UPROPERTY() FPP_SaveCharacterData  Character;
    UPROPERTY() FPP_SaveInventoryData  Inventory;
    UPROPERTY() FPP_SaveQuestData      Quests;
    UPROPERTY() FPP_SaveCheckpointData Checkpoint;
    UPROPERTY() FPP_SaveWorldData      World;
};
```

- 槽位名：`PP_Save_Slot0`，`UserIndex = 0`；偏好存档 `PP_LocalSettings` 保持独立，互不覆盖。
- 单档体积估算：物品按 50 条上限、任务按 20 条算，约 5–10 KB，同步读写开销可忽略；不引入异步保存。

### 2.3 版本号与兼容策略

- `constexpr int32 PP_SAVE_CURRENT_VERSION = 1`。
- 加载时三分支：
  1. `SaveVersion > Current`：拒绝加载，提示"存档来自更新版本的游戏"（不尝试猜字段）。
  2. `SaveVersion < Current`：依次执行 `Migrate_V1_To_V2`… 的函数链，每步只做确定的结构转换，缺失字段填默认值。
  3. `==`：直接使用。
- 版本升级规则（写进代码注释）：
  - 新增字段必须有类内默认值，旧档读出来是默认值 → 等价于"该功能从未使用"。
  - 删字段只做"停止赋值"，不从结构体删（至少保留一个大版本），避免旧代码回滚后读不了。
  - **数据表行名属于存档契约**：改行名等同于删档，加载时按行名查不到就跳过并告警（见 §6）。
- v1 是初始版本，`Migrate` 只留空壳与调用点，不预写不存在的版本。

### 2.4 损坏 / 缺失 / 覆盖

| 场景 | 处理 |
|---|---|
| 没有存档文件 | `LoadGameFromSlot` 返回 null → 视为无档，主菜单"继续游戏"置灰，不报错 |
| 反序列化失败 / Cast 失败 | 视为损坏；先尝试 `.bak`，仍失败则提示"存档已损坏"，开新档，不删除原文件 |
| 字段不合法 | `ValidateLoadedSave()`：版本区间、`MapName` 非空、数组长度上限、属性值 `FMath::IsFinite` 且 ≥ 0；不通过按损坏处理 |
| 保存覆盖 | 保存前把现有 `.sav` 复制为 `PP_Save_Slot0.bak`（`IFileManager::Copy`，路径 `FPaths::ProjectSavedDir()/SaveGames/`）；`.bak` 只保留一份 |
| 保存写到一半失败 | v1 记录 Error 并保留 `.bak`；不引入临时槽 + Move 的原子写（数据量小，收益低） |
| 蓝图/表行被删 | 不整体拒绝存档；按条目跳过并打 Warning，保证"能进游戏"优先 |

## 3. 保存/读取时机与触发者

所有写盘与数据应用都在**服务端**执行；客户端只发请求、收通知。

| 时机 | 触发者（权威侧） | 行为 |
|---|---|---|
| 篝火休息 | `APP_BonfireActor::Rest()` 末尾（现有函数，已确认终点） | 顺序：`SetCheckpoint` → `ResetAttributes` → **保存**。这样落盘的是满属性 + 新检查点 |
| 关卡切换 | `APP_CrashGameMode::ReturnToLobby()`，`ServerTravel` 之前 | 存一次；`SeamlessTravel` 若以后启用，也在同一处补 |
| 手动保存 | 暂停菜单"保存游戏" → `IPP_SaveActions::RequestSaveGame` → PC 的 `Server_RequestSaveGame` RPC → 服务端保存 | 成功后 `Client_NotifyMessage("已保存")`；失败提示原因 |
| 退出游戏 | `UPP_GameInstance::Shutdown()` | 最后保存一次。**PIE 下默认跳过**（`GIsPlayInEditor` 判定），否则每次 Stop 都会写盘污染测试存档 |
| 读档 | 主菜单"继续游戏"（大厅地图）→ `IPP_SaveActions::RequestLoadGame` → `UPP_SaveSubsystem` 读盘 + 标记 Pending → 走现有开局流程到 `MapName` | `APP_CrashGameMode::PostLogin` 应用玩家数据；`RestartPlayer` 后应用属性；世界状态在 `PostLogin` 内应用一次 |
| 读档次数 | `UPP_SaveSubsystem` 持 one-shot 标志 | 应用成功即清除 Pending；重生、重连、再次 Possess 不得重复应用（否则物品翻倍、属性叠加） |

`UPP_SaveSubsystem`（GameInstanceSubsystem，放 `PersonalProject` 模块）负责：快照采集、写盘、读盘、Pending 缓存、应用调度。放 GameInstance 是因为要跨 `ServerTravel` 存活，且大厅（LobbyMap）也要能读档。

## 4. 读档后的应用顺序（最容易写错的地方）

```text
PostLogin（服务端，优先于 Super 里的 RestartPlayer）
  1. 若 Pending：PS->SetSelectedCharacterId(存档角色)      // 必须先于 GrantAbilitiesForCharacter
  2. 应用背包 / 装备 / 金币（PS 上的组件，与 Pawn 无关）
  3. 应用任务进度
  4. 应用篝火检查点（PS->SetCheckpoint）
  5. 应用世界状态（采集点 / Boss / 门 / 魂）
Super::PostLogin → RestartPlayer → Pawn PossessedBy → InitializeAttributes（GE 初始化 base）
RestartPlayer 之后（服务端）
  6. 写入 9 项属性 base 值（此时 GE 初始化已完成，不会被覆盖）
  7. 若本次是读档：把 Pawn 传送到检查点（无检查点则保持 PlayerStart）
  8. 清除 Pending
```

第 6 步晚于 `InitializeAttributes` 是硬要求：早于它会被 `GE_InitializeAttributes` 覆盖，表现为"读档后血量满"。

## 5. 服务端/客户端职责与复制

### 5.1 边界

- 采集快照、写盘、改属性、改背包、遍历世界 Actor：**只在服务端**（`HasAuthority()` 守卫）。
- 客户端：暂停菜单只发 RPC；大厅主菜单只请求读档；结果通过现有 `Client_NotifyMessage` 显示。
- UI 不得直接拿 `GameMode` 做存档（客户端拿不到）；统一经 `IPP_SaveActions` 接口。

### 5.2 读档后必须重新复制给客户端的状态

| 数据 | 复制机制 | 备注 |
|---|---|---|
| `SelectedCharacterId` / `bHasCheckpoint` / `CheckpointTransform` | `PlayerState` 现有 `Replicated` | 已有 |
| `Items` / `EquippedItems` / `Gold` | `InventoryComponent` 的 `ReplicatedUsing` + `OnRep_*` | `OnRep_Equipped` 已负责刷新客户端武器外观，**不要绕过** |
| `ActiveQuests` / `CompletedQuestIDs` | `QuestComponent` 现有复制 | OnRep 刷新任务 UI |
| 9 项属性 | `AttributeSet` 的 `ReplicatedUsing` | 服务端 `SetNumericAttributeBase` 后自动同步 |
| 已装备 GE | ASC（Mixed 模式） | 服务端重建 `EffectHandle` 后随 ASC 复制到客户端 |
| 采集点剩余次数 | `RemainingGatherTimes` 现为 `Replicated` | 服务端写入后自动同步 |
| Boss 击败 / 场地门开启 | **目前没有复制**（见下） | 批次 4 补 |
| 魂 | `APP_SoulPickupActor` 为 `bReplicates`，服务端 Spawn 后自动复制 | 金额/Owner 也是 Replicated |

### 5.3 已发现的现有缺口（不是本次引入，但读档会放大）

- `APP_BossArenaGate` 没有 `bReplicates`，且靠 `EventBus` 的 `FPP_BossDeadEvent` 开门；EventBus 是进程内的，联机时客户端收不到 → 客户端看到门仍然关着。
- 处理：批次 4 给 Gate 加 `bReplicates = true` + `bOpen`（Replicated + `OnRep_bOpen` 应用碰撞/蓝图事件），读档和正常击杀都走同一个 `SetOpen()` 入口。Boss 侧新增 `bDefeated`（Replicated）以便客户端隐藏尸体/状态。

## 6. 蓝图资产引用怎么存

**原则：存档只存 ID，不存指针、不存软路径、不存类引用。**

| 运行时对象 | 存档里存什么 | 读档时怎么找回来 |
|---|---|---|
| 武器外观网格 / 武器 GA / 挂点变换 | 只存 `ItemID` | `DataManager->GetWeaponConfig(ItemID)` → `WeaponVisual` / `WeaponAbilityClass` |
| 装备属性 GE | 只存 `ItemID` | `GetItemInfo(ItemID)->EquipEffectClass` |
| 角色外观（网格 / 动画蓝图） | 只存 `CharacterId` | `GetCharacterData(CharacterId)`（表内是 `TSoftObjectPtr`，资产移动会自动更新引用） |
| 消耗品效果 GE | 只存 `ItemID` | `ConsumeEffectClass` |
| 任务目标 / 奖励 | 只存 `QuestID` + 运行时进度 | `GetQuestInfo(QuestID)`；目标签名按表校正 |
| 敌人 / Boss 数值与阶段 | 只存关卡 `ActorName` + `EnemyID`（诊断用） | 遍历关卡 Actor 按名匹配；数值本来就从 `DT_Enemies` 读 |
| 采集点 | `ActorName` + `GatherableID`（诊断用）+ 剩余次数 | 遍历关卡 Actor 按名匹配 |
| 篝火 | `CheckpointTransform` + `BonfireActorName`（诊断用） | 直接用 Transform 重生，不依赖篝火 Actor 还在不在 |
| 蒙太奇 | **不存** | 由角色/武器/装备配置间接决定 |

为什么这样不会因改名/移动失效：

- 资产在编辑器里改名/移动，`DataTable` 里的软引用与类引用会随编辑器自动修路径，存档里只有行名，不需要跟着改。
- 会失效的只有三种情况：**数据表行名被改**、**关卡 Actor 被改名/删除**、**资产被移出项目**。三种都在加载时按 `ValidateLoadedSave` + 逐条匹配做"跳过 + Warning"，不崩溃、不整体拒绝。
- 反例（禁止）：把 `TSubclassOf<UGameplayAbility>`、`UStaticMesh*` 塞进 `USaveGame`。那会让存档在资产改名后直接读到空引用，还会在加载时触发同步资产加载。

## 7. 与现有系统的接口

### 7.1 不用改

- `UPP_DataManager`：存档只存 ID，运行时照旧查表。
- `UPP_EventBus` 与事件结构：不改结构，读档完成后复用 `FPP_InventoryUpdatedEvent` / `FPP_EquippedUpdatedEvent` / `FPP_QuestsUpdatedEvent` 刷新 UI。
- GAS 的 GA/GE 资产、`AttributeSet` 的复制声明、`DT_*` 资产、所有 `.uasset`。
- `UPP_LocalSaveGame`（昵称偏好）与 `UPP_SessionManager`（大厅会话）。

### 7.2 新增

| 文件 | 模块 | 内容 |
|---|---|---|
| `Save/PP_SaveTypes.h` | Core | 上述全部 `FPP_Save*` 结构体 |
| `Save/PP_SaveGame.h/.cpp` | Core | `UPP_SaveGame` + 静态 `Load/Save/Backup/Migrate` 辅助 |
| `Interfaces/PP_SaveActions.h` | Core | `IPP_SaveActions`（BlueprintNativeEvent：`RequestSaveGame` / `RequestLoadGame` / `HasSaveGame`） |
| `Game/Save/PP_SaveSubsystem.h/.cpp` | PersonalProject | 快照采集、写盘、读盘、Pending、应用调度 |

### 7.3 修改（每处都尽量只加"恢复入口"）

| 文件 | 改动 |
|---|---|
| `PP_InventoryComponent` | 新增 `RestoreFromSave(const FPP_SaveInventoryData&)`（服务端） |
| `PP_QuestComponent` | 新增 `RestoreFromSave(const FPP_SaveQuestData&)`（服务端） |
| `PP_BonfireActor` | `Rest()` 末尾调保存；暴露 `GetBonfireName()` 供快照记录 |

| `PP_GameInstance` | `Shutdown()` 最后一次保存（PIE 跳过） |
| `PP_GatherableActor` | 新增 `GetRemainingGatherTimes()` + `ApplySavedState(int32)`（服务端） |

## 8. 分批实施（每批独立编译、独立验证、单独提交）

> 共同约束：只编译 `PersonalProjectEditor Win64 Development`；不 push；不改任何 `.uasset`；每批结束按 `workflow.md` 做 PIE 冒烟。

### 批次 1：骨架 + 角色进度（最关键的一批）

- 新建 `PP_SaveTypes` / `PP_SaveGame` / `IPP_SaveActions` / `PP_SaveSubsystem`；PC 的保存 RPC；`Exec` 调试命令 `PP_SaveGame` / `PP_LoadGame`；版本号、`ValidateLoadedSave`、`.bak` 备份。
- 实现：CharacterId、9 项属性、检查点的写入与还原（检查点在本批先落数据结构，读档落点也用上）。
- 验证：PIE 改血量 → `PP_SaveGame` → 退出 → 重开 → `PP_LoadGame`，血量/角色/落点一致；删掉 `.sav` 或写坏文件后读档不崩溃且有提示。

### 批次 2：背包 / 金币 / 装备

- `InventoryComponent::RestoreFromSave`：直接赋值 + 重建装备 GE + 广播事件。
- 验证：物品数量、堆叠、金币、已装备槽位 UI 一致；服务端与客户端武器外观一致（依靠 `OnRep_Equipped`）；装备加成的 MaxHealth/Attack **不双算**（背包/装备先恢复，属性后写 base）。

### 批次 3：任务进度

- `QuestComponent::RestoreFromSave`：按 `DT_Task` 校正目标签名后赋值，广播刷新。
- 验证：进行中任务的 CurrentCount、已完成任务列表与任务面板一致；表里删掉某任务后读档跳过该任务并告警，不崩溃。

### 批次 4：世界状态 + 复制缺口

- 采集点剩余次数、Boss 击败、场地门开启、魂的 Spawn；补 Gate/Boss 的复制缺口。
- 验证：采到剩 0 次的采集点读档后仍是耗尽态；已击败 Boss 读档后不复活且门是开的（含客户端）；死亡掉落的魂读档后仍在原位置、可拾回。

### 批次 5：时机收口 + 入口 + 兼容收尾

- 篝火自动保存、`ReturnToLobby` 前保存、退出保存（PIE 跳过）；主菜单"继续游戏"；暂停菜单"保存"。
- 迁移空壳与文档；编辑器清单核对。

## 10. 我认为最难 / 最容易出错的地方

按风险从高到低：

1. **属性 base 与装备加成的双算**。若先把属性写回再恢复装备，`EquipEffectClass` 的 Additive Modifier 会再叠一次，表现为读档后血量上限越读越高。方案：只存 `GetBaseValue()`，装备先恢复、属性最后写 base。
2. **应用时机**。`PostLogin` / `RestartPlayer` / `PossessedBy` / `InitializeAttributes` 的顺序一旦搞错，就是"读档后属性满血"或"角色ID 没生效导致能力集错"。本方案把属性写入固定在 `RestartPlayer` 之后，并在代码里注释说明原因。
3. **直接写装备数组绕过通知**。`EquippedItems` 直接赋值不会触发 `OnRep`/`NotifyEquipmentUser`，客户端武器外观与 GA 都不恢复。必须复用现有通知链路，或确保赋值后手动调一次。
4. **读档重复应用**。重生、重连、Possess 都会再次走到应用点，物品会被加两次。必须有 one-shot 标志。
5. **存档 Key 的稳定性**。世界状态依赖关卡 Actor 名和表行名，这两者是最容易被"顺手改名"破坏的契约；加载时必须"跳过 + 告警"，不能整体拒绝。
6. **EventBus 不跨网络 + Gate 未复制**。这是现有缺口，读档会把它暴露得更明显（客户端看到门没开）。批次 4 用 `bOpen` 复制补齐，顺带修掉正常击杀时的同一问题。
7. **PIE 退出误存盘**。`Shutdown` 在 PIE 也会触发，不跳过就会让"停止 PIE"覆盖掉手动存档。

## 11. 验收标准（可观测）

- 编译：`PersonalProjectEditor Win64 Development` 通过，无新增 Warning。

## 1. 目标形态

### 1.1 一套槽位枚举

**保留 `EPP_EquipSlot`，删除 `EPP_EquipmentSlotType`。**

| 旧枚举 `EPP_EquipmentSlotType` | 值 | 新枚举 `EPP_EquipSlot` | 值 |
|---|---|---|---|
| `PrimaryWeapon` | 0 | `MainHand` | 1 |
| `SecondaryWeapon` | 1 | `OffHand` | 2 |
| `Helmet` | 2 | `Head` | 3 |
| `Accessory` | 3 | `Ring` | 8 |

理由与约束：

- `EPP_EquipSlot` 的 9 个值已经被 `DT_Items.EquipSlot` 与 `FPP_EquippedItem.Slot` 序列化到资产里，**名称与数值都不能动**（不做 `MainHand → Primary` 这类"更整齐"的重命名，收益是零、风险是资产值错位）。
- `EPP_EquipmentSlotType` 只有 4 值、只被代码与少量蓝图 pin 使用，删除成本最低。
- `None = 0` 继续保留，作为"未指定槽"的默认值；**不要复用 0 号做武器槽**。
- 目标态槽位全集：`None / MainHand / OffHand / Head / Chest / Legs / Feet / Hands / Ring`（9 值）。缺 `Neck/Back` 之类，等有实际装备再加，**加在末尾**，不插空。

`FPP_EquipmentSlot` 结构整体删除；`FPP_EquippedItem` 保留（它已经等价于"槽位 + ItemID + 效果句柄"）：

```cpp
USTRUCT(BlueprintType)
struct FPP_EquippedItem
{
    GENERATED_BODY()

    UPROPERTY(BlueprintReadOnly) FName ItemID;
    UPROPERTY(BlueprintReadOnly) EPP_EquipSlot Slot = EPP_EquipSlot::None;

    /** 旧轨遗留：护甲 GE 句柄；B3 起统一迁到组件内的按槽 Map，字段保留仅为蓝图兼容 */
    UPROPERTY(NotReplicated) FActiveGameplayEffectHandle EffectHandle;
};
```

### 1.2 一套 RPC

`UPP_InventoryComponent` 上**只保留两个写入口**，签名不变（避免破坏既有蓝图节点）：

```cpp
/** 装备背包中的物品；槽位由 FPP_ItemInfo::EquipSlot 决定 */
UFUNCTION(Server, Reliable, BlueprintCallable, Category="Inventory|Equipment")
void Server_EquipItem(FName ItemID);

/** 装备到显式槽位；仅用于有双槽的武器（长剑可进主手或副手） */
UFUNCTION(Server, Reliable, BlueprintCallable, Category="Inventory|Equipment")
void Server_EquipItemToSlot(FName ItemID, EPP_EquipSlot PreferredSlot);

UFUNCTION(Server, Reliable, BlueprintCallable, Category="Inventory|Equipment")
void Server_UnequipItem(EPP_EquipSlot Slot);
```

服务端内部只有一个实现：

```cpp
/** 校验物品存在且可装备 → 解析目标槽 → 处理"同槽替换"→ 写 EquippedItems
 *  → 施加/移除 GE → 通知 IPP_EquipmentUser → 广播事件 */
void EquipItemInternal(FName ItemID, EPP_EquipSlot PreferredSlot);
```

槽位解析规则（写进实现注释，避免以后靠猜）：

1. `PreferredSlot != None` → 必须与 `ItemInfo.EquipSlot` 同类（武器槽可 `MainHand/OffHand` 互换），否则拒绝并打 Warning。
2. `PreferredSlot == None` → 用 `ItemInfo.EquipSlot`。
3. `ItemInfo.EquipSlot == None` 且是装备类 → 拒绝，Warning "物品未配置槽位"。

接口层同步：

- `IPP_InventoryActions` 只保留 `RequestEquipItem(FName)` / `RequestUnequipItem(EPP_EquipSlot)`（现在就是这么写的，不用改）。
- `IPP_EquipmentUser::OnEquipmentChanged` 参数由 `EPP_EquipmentSlotType` 改为 `EPP_EquipSlot`。**这是破坏性变更**：过渡期新增 `OnEquipmentChangedV2(EPP_EquipSlot, FName)`，旧函数保留并转发，蓝图重存后再删旧的。

### 1.3 一张武器配置表

**合并进 `DT_Items`**，`DT_WeaponData` 降级为过渡期只读镜像，最终删除。

```cpp

USTRUCT(BlueprintType)
struct FPP_WeaponVisual
{
    GENERATED_BODY()

    UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Weapon|Visual")
    TSoftObjectPtr<UStaticMesh> Mesh;

    UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Weapon|Visual")
    FName AttachSocket = FName("WeaponSocket");

    /** 伤害倍率，缺省 1.0；由伤害 Execution 读取 */

    UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Weapon")
    bool bCanUseOffHand = false;

USTRUCT(BlueprintType)
struct FPP_ItemInfo : public FTableRowBase
{
    // ... 现有字段保持不变（DisplayName/Description/ItemType/Icon/MaxStackCount/
    //     BuyPrice/SellPrice/ItemTags/EquipSlot/EquipEffectClass/Rarity/ConsumeEffectClass）

    /** 新增：武器专属配置 */
    UPROPERTY(EditAnywhere, BlueprintReadOnly, Category="Item|Weapon")
    FPP_WeaponConfig WeaponConfig;
};
```

三张表/映射的职责切分：

| 载体 | 目标职责 | 现状 | 处置 |
|---|---|---|---|
| **DT_Items** | 唯一权威：所有物品一行，武器行额外填 `WeaponConfig` | 通用字段齐全，缺武器字段 | 加 `WeaponConfig` 字段 |
| **DT_WeaponData** | 过渡期镜像，只读 | 武器 GA 的唯一来源 | A2 拷贝进 DT_Items；A4 停读；A5 删资产 |
| **`WeaponMeshMap`** | 无（字段并入 `DT_Items.WeaponConfig.Visual`） | 武器网格唯一来源，藏在 BP 默认值里 | A2 导出并写入 DT；A4 删属性 |

> 表名说明：`DT_Items` 是本文对"物品表"的简称，实际资产由 `UPP_DataManager::ItemDataTable` 指定，**需在编辑器确认**其真实资产名与路径；下文同。

新增一把武器的操作步骤（目标态）：

1. 导入网格资产；
2. 在 `DT_Items` 加一行，`RowName = ItemID`，填 `EquipSlot=MainHand`、`EquipEffectClass`、`WeaponConfig`（网格 / GA / 倍率）；
3. 若需要新技能，新建 GA 蓝图并在该行引用；
4. 若要在商店售卖，在商店表加一行（商店表的资产名与 `UPP_ShopComponent` 的配置方式**需在编辑器确认**）。

**C++ 零改动。** 网格用 `TSoftObjectPtr`，装备时同步加载（武器网格通常几 MB，一次性加载可接受）；若后续武器数量大，再改成异步预载——**需在编辑器确认包体与首次装备卡顿**。

## 2. 迁移路径（Branch by Abstraction）

总原则：**先数据、后代码、最后删旧**。每一段都能独立编译、独立运行、独立回滚。

### 阶段 A：配置合并（不改行为）

| 步 | 内容 | 中间态 | Commit 建议 |
|---|---|---|---|
| **A1** | 新增 `FPP_WeaponVisual` / `FPP_WeaponConfig`，`FPP_ItemInfo` 加字段；新增 `UPP_DataManager::GetWeaponConfig(FName)`，内部**先查 DT_Items，空则回退旧路径** | 新旧并存，运行行为不变 | `refactor(data): add weapon config to item rows with legacy fallback` |
| **A2** | 编辑器迁移工具：遍历 `DT_WeaponData` 行 + `BP_PlayerCharacter.WeaponMeshMap`，按 ItemID 写入 `DT_Items.WeaponConfig`；输出"已迁移 / 缺行 / 冲突"三张报告 | 数据双份，读取仍走旧 | `chore(editor): migrate weapon rows and mesh map into DT_Items`（工具代码）+ 单独一条数据提交 |
| **A3** | 角色改为通过 `GetWeaponConfig` 读技能与外观；`SetWeaponMesh` 不再查 `WeaponMeshMap`。回退分支保留并打 `[WeaponCfg] fallback used` 日志 | 新路径为主，旧路径兜底 | `refactor(weapon): read ability and visual from item data` |
| **A4** | 删回退分支、删 `WeaponMeshMap` / `WeaponDataTable` 两个 `UPROPERTY`；先在 BP 里把默认值导出留档，再删属性并重存蓝图 | 只剩 DT_Items | `refactor(weapon): drop weapon mesh map and legacy weapon table` |
| **A5** | 删除 `DT_WeaponData` 资产与 `FPP_WeaponData` 结构 | — | `chore(content): remove obsolete DT_WeaponData` |

**A4 的顺序不能反**：`WeaponMeshMap` 的值只存在于蓝图默认值中，删属性前必须先跑 A2 导出，否则数据丢失且无法从 git 恢复（蓝图二进制 diff 不可读）。

### 阶段 B：装备槽统一

| 步 | 内容 | 旧枚举 | 旧 RPC | `EquippedItems` 轨 | `EquipmentSlots` 轨 |
|---|---|---|---|---|---|
| **B1** | 内部统一实现 `EquipItemInternal`；两个旧 RPC 都转调；**双写** `EquippedItems` + `EquipmentSlots`（映射表 1.1） | 在用 | 在用 | 写 | 写 |
| **B2** | 读路径全切到 `EquippedItems`：`GetWeaponInSlot` / `GetEquipmentSlots` / `QueryEquippedItems` / UI 全部改为派生；加"两轨一致性"比对日志 | 在用 | 在用 | 读 + 写 | 只写 |
| **B3** | 停写 `EquipmentSlots`；删该复制属性、`OnRep_WeaponSlots`、`FPP_EquipmentSlot`；GA/GE 句柄 Map 的 key 改为 `EPP_EquipSlot`；新增 `OnEquipmentChangedV2` | 在用 | 转发 | 读写 | **删** |
| **B4** | 蓝图迁移：所有调用 `Server_EquipWeapon` 的节点（UI 装备按钮、`F9` 调试）改调 `Server_EquipItem`；旧 RPC 标 `DeprecatedFunction` 保留一个版本 | 在用 | 保留+弃用 | 读写 | — |
| **B5** | 删旧 RPC、删 `OnEquipmentChanged` V1、删 `EPP_EquipmentSlotType` | **删** | **删** | 读写 | — |

中间态要点：

- **B1 的双写必须走同一个函数**，不能"旧 RPC 写旧轨、新 RPC 写新轨"，否则幽灵态会持续到 B2。
- **B2 的一致性日志**是切换的安全绳：每次装备/卸下比对两轨内容，不一致就报 `Error` 并附槽位与 ItemID。跑满一整轮验收（含重生、双端）无 Error 才允许进 B3。
- **B3 是唯一有"停写"语义的一步**，也是回滚代价最高的一步（复制属性删了就要恢复）。B3 前打 tag。
- **B4 需要资产重存**，"节点的参数类型是否还合法"必须在编辑器里确认。

### 2.1 枚举序列化的规避方式

| 风险动作 | 后果 | 规避 |
|---|---|---|
| 给 `EPP_EquipSlot` 重命名（如改叫 `EPP_EquipmentSlot`） | 属性类型名变化，资产中枚举值可能回落默认 `None` | **不重命名**；即使以后要改名，必须配 `+EnumRedirects` 并逐个资产验证 |
| 重排/删除 `EPP_EquipSlot` 已有值 | 已存值含义整体错位（如 Head 变成 Chest） | 只允许**末尾追加**；本次一个值都不动 |
| 删除 `EPP_EquipmentSlotType` | 蓝图 pin 变成 `None`/编译错误 | B4 先移除所有引用（含 BP 节点与接口实现），B5 再删；删前用 AssetRegistry 搜索类名，**需在编辑器确认** |
| 把 `FPP_EquipmentSlot` 删掉但蓝图仍在用 | BP 结构体 pin 断链 | 同步 B3，删前导出所有引用了该结构的设备/UI 蓝图 |
| 给 `FPP_ItemInfo` 加字段 | 安全（DataTable 行结构加字段是增量） | 无需处理；但**不要删字段**，`EquipSlot` 尤其不能删 |

## 3. 物品侧的对应改动

### 3.1 消掉"ItemID 与 RowName 三处一致"

现状是**四处**手工一致：`DT_Items.RowName`、`FPP_ItemInfo.ItemID`、`DT_WeaponData.RowName`、`FPP_WeaponData.ItemID`，外加代码里的调试常量（`DebugPrimaryWeaponItemID`）。合并后降为两处：`RowName` 与 `ItemID`。

分三层解决：

| 层 | 做法 | 触发时机 |
|---|---|---|
| **运行时** | `UPP_DataManager::ValidateItemTables()`：遍历所有行，`RowName != ItemID` 记 Error 并统计；`GetItemInfo` 查不到时 Error（现在只有 Warning） | `GameInstance::Init` / 首次取表 |
| **编辑器** | 迁移工具附带"一键修复"：把 `ItemID` 覆写为 `RowName`（只改空值或确认不一致的行），输出修改清单 | 手动执行 |
| **数据约束** | 武器行额外校验：`EquipSlot ∈ {MainHand, OffHand}`；`Visual.Mesh` 非空；`WeaponAbilityClass` 为空时必须在行备注里说明"纯属性武器" | 同上 |

不采用"删除 `ItemID` 字段、只留 RowName"：`ItemID` 已被蓝图读取（背包/商店/任务），删字段是破坏性变更，收益只是省一个字段。**保留字段 + 启动校验**是成本最低的解。

### 3.2 `AbilityTags` 与 `DamageMultiplier`

| 字段 | 判断 | 理由 |
|---|---|---|
| **`AbilityTags`** | **删除** | ① 零消费方；② 武器技能已由 `WeaponAbilityClass` 唯一定位，再加 tag 是第二套身份标识；③ 若将来需要"武器类型"（剑/斧/枪）参与伤害或动画选择，应该是一个 `FGameplayTag WeaponType` 单值字段，而不是复数数组，且要有明确消费方才加 |
| **`DamageMultiplier`** | **保留并补消费方** | ① 它是魂类武器差异最直接的数值旋钮，删了迟早要加回来；② 现在"存在但没人读"比"不存在"更糟——它会让人误以为改了有效。补消费方的落点：`UPP_DamageExecution` 里由 Source ASC → Pawn → Inventory 主手 ItemID → `GetWeaponConfig().DamageMultiplier`，缺省 1.0 保证空手与旧数据不回归 |

**前置确认（需在编辑器）**：`DT_WeaponData` 里 `AbilityTags` 是否已有非空值、`DamageMultiplier` 是否全为 1.0。若 `AbilityTags` 有非空值，先查蓝图 GA 是否按 tag 匹配；有匹配则改为读 `WeaponAbilityClass`，无匹配直接删。

补消费方的验收：同一把武器把倍率从 1.0 改 2.0，木桩伤害翻倍；改回 1.0 恢复。这是唯一能证明"字段被消费"的方法。

### 4.2 必须整体回滚的情形

只在以下情况回滚到上一个 tag，而不是单条 revert：

1. **资产序列化事故**：打开 `DT_Items` 或装备蓝图后，`EquipSlot` 大面积变成 `None`，或武器字段丢失。
2. **双端状态分叉**：同一操作在主机与客户端显示不同，且重进关卡仍不同。
3. **属性漂移**：换装 N 次后属性叠加或回不到基线（GE 句柄泄漏）。
4. **GA 重复**：技能栏出现两个同名技能，或卸下后技能仍可用。

单条可回滚的（不构成整体回滚）：编译失败、日志告警、迁移报告缺行、编辑器工具报错。

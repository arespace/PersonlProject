> 状态：细节参考 · 最后更新：2026-11-06 · 取代关系：无（排期顺序以《当前主线任务书》P0–P6 为准）
> 编号说明：本文的 `S0`–`S10` 为旧编号，已废弃；映射关系见《当前主线任务书》§0，读到旧编号请对照，不要按旧编号开工。
> 基线：`e941461`（2026-11-06，Core/Framework 目录拆分之后）
> 范围：5 模块（Core / Inventory / Quest / PersonalProject / UI），约 2.5 万行 C++

## 1. 总览

### 1.1 五条主线

| 主线 | 内容 | 与其它主线的关系 |
|---|---|---|
| A 角色装配化 | 玩家角色拆组件（锁定/武器外观/耐力）+ 输入配置资产 | 依赖安全网；是装备统一的前置 |
| B 数据契约与配置单一化 | 角色/武器/Boss/技能槽收敛到表，消除多处 FName 同步 | 依赖装备统一；是存档实现的前置 |
| C 边界与编译期清理 | 公开头瘦身、UIGateway 拆分、死代码与孤岛资产 | 独立，可与 A 前后脚执行 |
| D 运行时语义 | 联机事件、流程状态机、存档、事件生命周期 | 依赖 A/B 完成后的稳定数据结构 |
| E Core 拆分 | Infra 与 GameplayCore 拆成插件 | 依赖全部完成，**现在不做** |
| S 安全网 | 数据校验、日志、边界脚本、事件弱引用、冒烟基线 | 所有主线的前置，必须先做 |

### 1.3 为什么是这个顺序

1. **S0 必须最先**：联机从未验证、蓝图属性未快照、资产未备份。没有基线，后面每一步都无法判断「是改坏了还是本来就这样」。
2. **S1 先于所有结构改动**：数据校验器是后续所有数据化改动的安全网；事件弱引用和旅行清空保护所有新增订阅；死代码不先删，输入配置和角色组件化要改两份。
3. **S2 与 S3/S4 可交换，但不能同时**：S2 是纯编译期改动，面广但风险低；S3/S4 是行为改动。单人开发一次只做一类，避免编译错误和行为错误混在一起难以定位。
4. **S5 必须在 S4 之后**：武器外观组件抽出来后，装备槽统一才有单一落点；否则要在 God Class 里同时改外观、GA 和槽位。
5. **S6 在 S5 之后**：武器表要增加网格/挂点字段，必须等槽位和数据形状稳定。
6. **S7 在 S1 之后、UI 大改之前**：事件结构一旦去掉 `APlayerController*`，所有订阅方都要改，越晚成本越高。
7. **S8 在 S7 之后**：流程状态需要复制通道，否则四人房间各端状态不一致。
8. **S9 在 S5/S6 之后**：存档格式依赖最终的背包/装备/任务结构；契约可以先定，实现必须后置。
9. **S10 不排期**：拆 Core 会触碰 94 条重定向、974 个已入库资产和蓝图父类，风险远大于当前收益。

### 1.4 本计划明确不做的事

- 不新增第 6 个模块，不做 Core 插件化（S10 仅保留条件）。
- 不整体替换 ALS、不引入 StateTree 大改、不引入第三方战斗框架。
- 不在架构批次里顺手做玩法功能；新增功能一律排到批次之外。
- 不在同一批次里同时改代码和批量移动资产。

## 3. 阶段门

### 3.1 通用出口条件

任何阶段进入下一阶段前，以下条件必须全部成立：

1. 全量编译通过（关闭编辑器），零新增 warning。
2. 数据校验器 0 错误。
3. 冒烟清单（附录 B）全部通过。
4. 编辑器启动日志无 `Failed to load Class/Parent`、无蓝图编译错误。
5. `git status` 干净，当前批次已形成单个 commit。
6. 批次记录（附录 D）已填写：改了什么、验证了什么、遗留什么。

### 3.2 阶段专属门

| 阶段 | 进入下一阶段的条件 |
|---|---|
| S0 → S1 | 双客户端 PIE 通过；备份完成；属性快照完成 |
| S1 → S2 | 校验器能报错；边界脚本能拦截；死代码删除后无加载错误 |
| S2 → S3 | 全量编译通过；UI 面板回归通过；边界脚本 0 违规 |
| S3 → S4 | 输入全部通过；新角色只换资产 |
| S4 → S5 | 三个子批次各自 PIE 通过；蓝图属性逐项核对无丢失 |
| S5 → S6 | 装备矩阵全部通过；客户端外观同步通过 |
| S6 → S7 | 新角色/新武器只改表即可运行 |
| S7 → S8 | 双客户端事件全通；无重复事件 |
| S8 → S9 | 四人流程状态正确；无卡死 |
| S9 → 完成 | 存读档全通；版本兼容策略生效 |

### 3.3 必须回滚而不是继续的情况

出现以下任一情况，停止当前批次，回滚到批次起点 commit，重新拆解：

- 编辑器启动出现资产父类加载失败，或蓝图大面积「类未设置」。
- 已确认蓝图属性值丢失（例如 `WeaponMeshMap` 变空、`StartupAbilities` 清空）。
- 核心流程（移动/技能/死亡/复活）在 PIE 中崩溃，且一次修复后仍复现。
- 同一问题连续两次修复失败，根因仍不明确。
- 改动文件数超过卡片预估 30%，说明批次边界失控。
- 性能相对 S0 基线退化超过 20%，且定位不到单点原因。

回滚动作：`git revert` 到批次起点；若涉及资产，使用 `_Backups` 恢复，不依赖 git 合并；记录失败原因后再拆成更小批次。

## 4. 与另外两份清单的关系

### 4.1 与《Content 资产整理方案》（4 个批次）

| Content 批次 | 内容 | 与本计划的文件冲突 | 建议 |
|---|---|---|---|
| 批次 0 清理 | 删 redirector、归档无引用资产 | 与 S1 的死代码/孤岛删除**争抢同一批资产**（ALS 孤岛、死 Widget、无用 UI 素材） | **合并进 S1**：先做引用扫描，再归档，最后删 C++ 类 |
| 批次 1 目录收口 | 小目录归位、UI 分类细化 | 与 S2 的 UI 头/网关改动不冲突，但会改资产路径 | 放在 S2 完成后、S3 之前，单独一个资产批次 |
| 批次 2 大范围迁移 | UI 素材包搬家、角色动画目录重整 | 与 S4（角色外观/动画）、S2（UI）**争抢 UI 蓝图与动画资产** | **错开**：S4 完成后、S5 之前做；S4 期间冻结资产移动 |

## 5. 每批次的标准动作

每个批次固定执行以下 8 步，顺序不可省：

### 5.1 开工声明

在批次记录（附录 D）顶部写清：

- 批次编号与名称
- 目标（一句话）
- 预计改动文件清单（超过 10 个必须拆批）
- 前置批次是否已通过
- 需要的蓝图配置项
- 回滚 commit
- 预计理想工时

### 5.2 改前基线

1. `git status` 必须干净，记录 HEAD。
2. 全量编译一次，记录耗时与 warning 数。
3. 运行数据校验器，记录错误数。
4. 备份 `Content` 与 `Config`（批次涉及资产时）。
5. 导出本批次会迁移的蓝图属性值（附录 C）。

### 5.3 实现

- 只改开工声明里列出的文件。
- 不做顺手重构、不重命名无关类、不调整格式。
- 涉及类名/命名空间变化时，先加 CoreRedirects，再改代码。

### 5.4 编译

- 仅改 `.cpp` 函数体：可用 Live Coding 快速验证。
- 新增/修改 `UPROPERTY`、`USTRUCT`、RPC、类移动/重命名：**关闭编辑器和所有 PIE 窗口**后全量编译。
- 编译必须零新增 warning；有 warning 先修，不进入下一步。

### 5.5 蓝图配置

- 打开编辑器，按开工声明逐项配置。
- 若出现「组件类未设置 / 父类加载失败」，**立即停止并检查重定向，不得保存蓝图**。
- 配置完成后，重新打开相关蓝图确认引脚与默认值。

### 5.6 PIE 冒烟

按附录 B 的固定清单逐项执行；联机相关批次必须双客户端；角色相关批次必须验证死亡→复活。

### 5.7 审查

- 运行 `_tools/CheckModuleBoundaries.ps1`，必须 0 违规。
- 自查：是否有跨模块具体类引用、是否有新增 God 方法、是否有事件未退订、是否有硬编码资产路径。
- 涉及接口变更的批次，检查所有实现类是否同步。

### 5.8 一次提交

- 一个批次一个 commit，代码与必要的蓝图配置说明一起提交。
- 提交信息格式：`refactor(<模块>): <批次号> <一句话目标>`。
- 提交后回填批次记录：实际工时、偏差、遗留项、下一步。

## 6. 风险专项

### 6.1 蓝图断引用与属性值丢失

**机制**：C++ 类重命名/移动/删除、接口拆分、属性从角色搬到组件，都会让蓝图里的类引用或已保存值失效。最隐蔽的是「蓝图编译能过，但默认值变空」。

**高发批次**：S1（删类）、S2（拆接口）、S4（属性迁移）、S5（槽位枚举替换）。

**预防**：

1. 删 C++ 类前，先在编辑器里把所有引用它的蓝图父类改掉或归档，确认启动日志无 `Failed to load`。
2. 属性迁移前导出快照，迁移后逐项核对：`WeaponMeshMap`、`WeaponAttachSocketName`、`BuiltInWeaponMaterialSlots`、`HiddenWeaponMaterial`、`StartupAbilities`、`WeaponDataTable`、`DebugPrimaryWeaponItemID`、HUD/GameMode 的所有 Widget 类。
3. 类名不变、只改实现时，不要动头文件路径；必须动时先加 CoreRedirects。
4. 出问题先回滚代码，再从备份恢复蓝图，不在损坏的蓝图上继续保存。

### 6.2 CoreRedirects 与资产重存

**现状**：`DefaultEngine.ini` 有 94 条重定向；Content 已入库但为二进制。

**规则**：

1. 任何类重命名/移动，先写重定向，再改代码，再启动编辑器验证。
2. 重定向的反射路径要去掉类型前缀（`UPP_Xxx` → `PP_Xxx`，`APP_Xxx` → `PP_Xxx`），枚举保留前缀。
3. 资产移动只用编辑器内 `EditorAssetLibrary`，不用 PowerShell 直接搬 `.uasset`。
4. 资产移动后执行一次引用修复 + 递归保存 + Asset Registry 刷新。
5. 重定向清理单独做，不在结构批次里顺手删。

### 6.3 Live Coding 分界

| 改动类型 | 能否热更 | 处理方式 |
|---|---|---|
| 仅 `.cpp` 函数体 | 可以 | Ctrl+Alt+F11 快速验证 |
| 新增/修改 `UPROPERTY` | 不可以 | 关编辑器全量编译 |
| 新增/修改 `USTRUCT` / 枚举 | 不可以 | 关编辑器全量编译 |
| 新增/修改 RPC / 复制属性 | 不可以 | 关编辑器全量编译 |
| 类重命名/移动/删除 | 不可以 | 关编辑器 + 重定向 + 全量编译 |
| 函数内 `static` 变量 | 不重置 | 调试用局部变量，不依赖热更 |

批次计划必须为此预留「停编辑器」窗口；S2、S5、S7 基本全程需要关编辑器。

### 6.4 资产级回滚只能靠备份

- git 能记录资产，但 `.uasset` 冲突不可合并，回滚粒度和可读性都差。
- 每个涉及资产的批次开始前，复制 `Content` 到 `_Backups/PersonalProject_<日期>_<批次>`。
- 资产删除/移动后出问题，从备份整体恢复，不用 git checkout 单个文件。
- 备份在批次验收通过后再清理，至少保留最近两个批次。

### 6.5 并行开发与二进制冲突

- 结构性批次执行期间，冻结其他窗口的功能开发。
- 若必须并行，只允许改与本批次不重叠的目录（例如纯 UI 文案、动画资产），且不提交同一批蓝图。
- 两个分支改同一个 `.uasset` 时，只能人工二选一，不能 merge。

## 7. 容易漏掉的准备项

以下内容在架构报告里没有展开，但执行前必须准备好：

### 7.1 工程准备

- **资产引用扫描**：对每个将要删除/移动的类名和资产名做一次全 Content 字符串检索，确认引用方；扫描结果留档。
- **蓝图属性快照**：导出附录 C 的表格，包含当前值、所属蓝图、迁移目标组件；迁移后逐项对比。
- **LFS 状态确认**：`git lfs status`、干净 clone 后能否打开工程；确认 `.uasset` 走 LFS 而不是普通二进制。
- **编辑器与引擎版本锁定**：记录 UE 5.7 的具体小版本和插件版本，批次期间不升级。
- **工具可用性**：PowerShell、Python（Editor Scripting）、`_tools` 下脚本能正常运行。
- **备份路径**：`_Backups` 有足够磁盘空间，命名规则统一。

### 7.2 验证准备

- **冒烟清单**（附录 B）必须覆盖：登录、大厅、选角、旅行、移动、技能、受击、死亡、复活、篝火、拾取、商店、任务、Boss、结算、返回大厅。
- **双客户端基线**：在 S0 就确认能跑；如果当前跑不通，先修联机基线，不进入 S7。
- **基线数据**：编译耗时、PPMap 平均帧时间、内存峰值、Actor 数、Draw Call 数；没有基线就无法判断性能是否退化。
- **日志观察点**：启动日志中的资产加载错误、蓝图编译错误、`Ensure`/`Warning` 数量。

### 7.3 产品侧决策（会影响架构取舍）

- **目标平台与画质目标**：决定是否值得为武器表做软引用、是否要控制同屏 Actor 数。
- **目标帧率与分辨率**：决定 HUD 每帧扫描、Canvas 绘制是否必须改。
- **联机规模与形态**：4 人房间是否固定；是否需要中途加入、掉线重连；这决定 S7/S9 的范围。
- **存档粒度**：只存角色进度，还是存世界状态；决定 `IPP_SaveParticipant` 的覆盖面。
- **是否做多语言**：决定现在是否要把硬编码中文通知收进表。
- **是否要跨项目复用 Core**：决定 S10 是否进入排期。

### 7.4 流程准备

- **单窗口串行约定**：结构批次期间只开一个执行窗口，其它窗口只读不改。
- **提交窗口**：每批次结束统一提交，不在批次中途提交半成品。
- **批次记录模板**（附录 D）先建好，避免事后补记。
- **失败预案**：明确「回滚到哪个 commit、从哪个备份恢复、由谁决定继续」，避免出问题时临场判断。

## 4. 迁移顺序

### 第 1 批（必须先做，风险最低、收益最高）

| 顺序 | 项 | 理由 | 验证 |
|---|---|---|---|
| 1.1 | 敌人/Boss 数值 → `DT_Enemies` | 8+5 项零散属性、逐蓝图手填，是当前最大的数据空档；`DT_Items` 已示范了"表 + ID 查询"的完整路径，可直接复用 `UPP_DataManager` | 改表内一行血量 → PIE 进同一关卡，敌人血量随之变化，**不重编译** |
| 1.2 | 掉落配置 → `DT_Enemies.DropItemID` | 与 1.1 同表，顺手完成；当前 ItemID 写死在敌人上，改掉落要开蓝图 | 改掉落后击杀，掉落变化 |
| 1.3 | 采集点 → `DT_Gatherables` | 5 项实例属性，改动频率高；只影响单个 Actor 类，波及面小 | 改刷新时间 → PIE 采完等刷新 |

### 第 2 批（并行可行）

| 顺序 | 项 | 理由 | 验证 |
|---|---|---|---|
| 2.1 | 角色成长（耐力 5 列 + 翻滚 2 列 + 锁定 5 列）→ `DT_Characters` | 现在散在三个类上，且 BP 与 C++ 各存一份（见任务书 P4.1 的 deprecated 属性）；一并迁移可同时消掉"两份显示" | 改表内 `RollStaminaCost` → PIE 翻滚两次体力见底，不重编译 |
| 2.2 | `AbilitySet` → `DT_Characters` | 现在在 `PP_CrashGameMode` 的 `TMap` 里，换角色要改 GameMode | 换一行 AbilitySet → PIE 技能栏变化 |

### 第 3 批（可延后）

| 顺序 | 项 | 理由 |
|---|---|---|
| 3.1 | 篝火 / 场景参数 → `DA_BonfireSettings` | 每关实例少，改动频率低 |
| 3.2 | 初始装备 / 初始金币 → `DT_Characters` | 依赖背包与存档结构，等 P5.1 存档前置更划算 |

### 不迁

- ALS 的 IMC 与 13 个 IA、`ConstructorHelpers` 兜底路径（`PP_ALSPlayerCharacter.cpp:38-145`）；
- 输入键位与 `IA` 引用（P4.3 已封版，避免二次搬动）；
- UI 布局与 WBP 绑定；
- `DT_ShopInventory` 与 NPC 对话表（实例级，语义正确）。

## 5. 迁移后如何验证"改数据不用重编译"

1. **单表校验**：跑 `PP_DataValidator`，确保新表的行主键、外键（`ItemID` / `EnemyID` / `CharacterId`）都能在目标表里找到；缺失即 Error。
2. **热改验证**：PIE 运行中改 `DT` 某一行 → 触发一次重新读取（或重开 PIE），观察行为变化；全程不编译 C++。
3. **交叉引用校验**：敌人表里的 `DropItemID` 必须命中 `DT_Items`；角色表的 `AbilitySet` 必须命中 GA 父类；这两条建议加进 `PP_DataValidator`。
4. **回退**：每张表迁完单独提交；出问题只需回滚该提交，不影响其它表。

## 6. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 表行名与蓝图里写死的 ID 不一致 | 运行期静默取默认值 | 迁移时先导出全部现有蓝图取值，逐项对照；校验器加"空 ID"检查 |
| `FPP_ItemInfo` 已有 `WeaponConfig` 内嵌结构，敌人表若也内嵌武器配置会重复 | 双份数据源 | 敌人表只存 `ItemID`，不复制武器字段 |
| 角色表新增列会让旧行反序列化缺列 | 默认值静默生效 | 新列必须有非零默认值，并在表里逐行显式填 |

## 0. 结论先行

- **总时长**：U0–U7 合计约 **60–75 小时**；U8 为触发式后置阶段，不计入当前预算。
- **顺序**：工程导航 → GAS → 移动/ALS → 动画与 Root Motion → 输入与生命周期 → 复制与网络 → 数据与领域模块 → UMG。
- **最该先学**：GAS（U1）、移动/ALS（U2）、动画与 Root Motion（U3）。理由是当前重构的耐力、武器、翻滚全部落在这三条链路上，且它们是最不容易被重构推翻的引擎机制。
- **明确后置**：武器外观组件、配置数据化、流程状态机、存档、联机事件化。前置条件与教材见 [§4](#4-后置阶段触发式)。

## 1. 使用方法

### 1.1 三遍读法（防止「从 Engine/Source 第一行开始读」）

| 遍数 | 只做什么 | 不做什么 |
| --- | --- | --- |
| 第一遍：追调用点 | 从项目里的一个函数出发，只追它调到的引擎函数，画出 3–5 个节点的调用链 | 不读引擎函数内部实现 |
| 第二遍：读主路径 | 只读该引擎函数的主干分支（正常流程），跳过平台分支、编辑器分支、废弃分支 | 不逐行注释，不追宏展开 |
| 第三遍：读边界 | 读网络/生命周期/异常路径：谁在服务器、谁在客户端、失败时回滚什么 | 不扩大到无关子系统 |

**铁律**：每读一个引擎函数，必须回到项目里找到至少一个调用点或配置点。找不到就说明这个知识点当前用不上，先放下。

### 1.2 每个单元的交付物（三选一，必须留下证据）

1. **链路口述**：不看代码，3 分钟内讲清 A→B→C，并指出哪一步在服务器、哪一步在客户端。
2. **后果预判**：写出「如果把 X 改成 Y，Z 会怎样」，并给出机制层面的原因；随后用只读方式验证。
3. **最小实验**：用 PIE、控制台、断点或临时日志，观察到一个具体值、顺序或状态变化。

没有交付物就不算完成。**「读完某个文件」不是里程碑。**

### 1.3 只读实验边界

允许：

- PIE 内控制台命令（`showdebug abilitysystem`、`showdebug character`、`ShowDebug Animation`、`stat net` 等）。
- 调试器断点、watch、调用栈。
- 临时 `UE_LOG`（验证后立即删除，不提交）。
- 读取 `Intermediate/` 下的生成文件、编辑器内的资产检查器。

不允许：

- 改 `Source/`、`Config/`、蓝图、数据资产后提交。
- 为了让实验跑通而临时改 GameMode、默认地图、输入映射并保留。
- 编译或打包（学习阶段不需要；除非你正在验证构建相关知识点，且验证后还原）。

### 1.4 路径约定

- 项目路径相对仓库根，例如 `Source/PersonalProject/Private/Characters/PP_PlayerCharacter.cpp`。
- 引擎路径统一写成 `Engine/Source/...`，相对本机引擎根 `d:\Ue\UnrealEngine\UE_5.7\`。
- 特例：
  - GAS 在 `Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities/...`
  - Enhanced Input 在 `Engine/Plugins/EnhancedInput/Source/EnhancedInput/...`
  - 项目内 ALS 插件在 `Plugins/ALS/Source/ALS/...`

## 2. 项目现状快照（只写会活下来的部分）

### 2.1 五模块单向依赖

依赖方向：

```
PersonalProjectCore ← PersonalProjectInventory ← PersonalProjectQuest ← PersonalProject ← PersonalProjectUI
```

| 模块 | 职责 | Build.cs 公开依赖 | 稳定度 | 关键类 |
| --- | --- | --- | --- | --- |
| `PersonalProjectCore` | 引擎接入层：ASC/AttributeSet、角色基类、事件总线、数据管理、会话、共享数据类型 | Engine、GameplayTags、GameplayAbilities、ALS、OnlineSubsystem | 高 | `APP_BaseCharacter`、`UPP_AbilitySystemComponent`、`UPP_AttributeSet`、`UPP_EventBus`、`UPP_DataManager`、`UPP_SessionManager` |
| `PersonalProjectInventory` | 背包/装备/商店/采集的领域逻辑 | Core、GameplayAbilities | 高（单轨已收敛） | `UPP_InventoryComponent`、`UPP_ShopComponent`、`APP_GatherableActor` |
| `PersonalProjectQuest` | 任务状态机与任务事件桥 | Core、Inventory | 中 | `UPP_QuestComponent`、`UPP_QuestEventBridge`、`APP_NPCActor` |
| `PersonalProject` | 玩法装配：玩家/敌人/Boss、控制器、GameMode、技能实现、UI 网关接口 | Core、Inventory、Quest、ALS、ALSExtras、ALSCamera、EnhancedInput、UMG、GAS | 中（重构主战场） | `APP_PlayerCharacter`、`APP_PlayerState`、`APP_PlayerController`、`UPP_LockOnComponent`、`UPP_GameplayAbility` |
| `PersonalProjectUI` | HUD、Widget 栈、ViewModel、Widget 池、跨模块 UI 实现 | Core、Quest、PersonalProject、UMG、Slate | 中 | `APP_HUD`、`UPP_UIManager`、`UPP_UIUserWidget`、`UPP_UIViewModel` |

**读 Build.cs 时重点看三件事**：

1. `PublicDependencyModuleNames` 与 `PrivateDependencyModuleNames` 的差别：前者会把依赖传递到下游模块的头文件搜索路径，后者只在本模块 cpp 内可见。用错会把模块边界「泄漏」出去。
2. `PCHUsage = PCHUsageMode.UseExplicitOrSharedPCHs`：共享 PCH 让编译变快，但也意味着头文件包含顺序和宏污染更隐蔽。
3. 主模块里 `if (Target.bBuildEditor)` 包裹的 `UnrealEd`/`AssetTools`：这些是编辑器工具依赖，运行时模块不应依赖它们。

> 这五条边界不会因为「拆组件」而改变。拆组件改的是模块内部结构，不是模块之间的依赖方向。
